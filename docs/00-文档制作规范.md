# 文档制作规范

| 项 | 内容 |
|---|---|
| 文档编号 | 00（本规范为元文档，固定占用 00） |
| 文档状态 | 已定稿 |
| 适用范围 | 本项目工作区内 `docs/` 目录全部文档，及全项目的文件架构、产物与 git 规范 |

> 本规范生效后，所有新建/修改文档及项目文件均须遵守；
> 规范本身的修改同样走 git 提交留痕。

---

## 1. 命名规范（首要规范）

### 1.1 文件名格式

```
NN-文档名称.md
```

- `NN`：两位数字序号，**必须写在文件名最前面**；
- `文档名称`：中文短名（建议 ≤ 20 字），见名知义；
- 中文与数字、多段名称之间用连字符 `-` 分隔；
- 示例：`01-项目文档-SOP-AI防错智检系统.md`。

### 1.2 序号分配规则

| 规则 | 说明 |
|---|---|
| 起始 | `00` 固定给本规范（元文档），业务文档从 `01` 起按创建顺序递增 |
| 唯一 | 序号一经分配不得变更；文档删除后其序号**作废，不得复用** |
| 不重排 | 新增文档插到已有文档之间时，不重排现有序号，新文档取下一个可用序号 |
| 阅读顺序 | 文档间的阅读/依赖顺序由 §6「文档清单」维护，不靠序号表达 |

### 1.3 字符限制

- **允许**：中文、英文字母、数字、连字符 `-`；
- **禁止**：空格及一切特殊字符（`/ \ : * ? " < > |` 为 Windows 非法字符；空格虽合法仍禁止——本工作目录路径已含空格 `Sop demo to Tianjun`，文件名再含空格会加重命令行转义负担）；
- **禁止**把版本号、日期、作者名写进文件名——历史信息一律由 git 管理（§4）。

### 1.4 导出副本（PDF / Word）

- 对外交付需要 PDF/Word 时，导出文件放入 `exports/` 目录（不进 `docs/`，且不入 git）；
- 源 `.md` 与导出副本不一致时，以 `docs/` 内源文件为准。

## 2. 结构规范

### 2.1 头部信息表（必备）

每份文档正文第一级标题之后，紧跟信息表：

```markdown
| 项 | 内容 |
|---|---|
| 文档编号 | NN |
| 文档状态 | 草稿 / 评审中 / 已定稿 |
| 关联文档 | [NN-xxx](./NN-xxx.md)（如有） |
```

**版本号与修改历史不写入文档**——全部由 git 提交历史管理（§4）。

### 2.2 章节编号

- 章节用多级阿拉伯数字编号：`1` / `1.1` / `1.1.1`，对应 Markdown 标题 `##` / `###` / `####`；
- 编号层级不超过四级；一级标题 `#` 只用于文档名本身。

### 2.3 其他结构要求

- 超过 300 行的文档，在信息表后加目录；
- **待确认问题、风险必须单列成章**，不得散落在正文中。

## 3. 写作规范

| 规则 | 说明 |
|---|---|
| **过时内容直接删除** | 不留痕迹：不写「已废弃」「已移除」「原为…」等说明文字，历史由 git 保留 |
| 语言 | 中文为主；专业术语首次出现时标注英文原文（如 mAP，平均精度均值） |
| 结论前置 | 每章首段先给结论/要点，再展开细节 |
| 事实表达 | 指标、清单等用表格；命令、路径、代码一律用代码块，不写进叙述句 |
| 链接 | 文档间引用一律写 Markdown 相对链接并带上完整文件名（含序号） |
| 一致性 | 同一概念全文用同一叫法（如统一叫「工位工作站」，不混用「客户端/终端软件」） |

## 4. Git 规范

- 仓库位置：项目工作区根目录，主分支 `main`；
- **一切修改通过 git 提交留痕**，文档内不写变更记录、版本号；
- 提交信息前缀约定：

| 前缀 | 用途 |
|---|---|
| `docs:` | 文档新增/修改 |
| `feat:` | 功能代码 |
| `fix:` | 修复 |
| `chore:` | 配置、构建、环境类杂务 |
| `data:` | 数据集准备（脚本、转换配置） |
| `archive:` | **归档操作**（过时产物移入 `archive/`，见 §5） |

- **过时/废弃的中间产物自动归档后，必须以 `archive:` 提交一次 git，表示归档动作发生**；
- 大文件不入库：`.venv/`、`datasets/`、`runs/`、`archive/` 内的二进制数据与模型权重均在 `.gitignore` 中排除；git 只跟踪代码、文档、配置与归档清单 `archive/ARCHIVE_LOG.md`。

## 5. 文件架构与产物规范（重点）

**原则：一个文件只允许出现在它所属的目录里。不允许出现「到处都是脚本」「中间产物散落」的情况。**

```
项目根目录/
├── docs/                 # 全部文档（§1–§3 约束）
├── src/                  # 项目源代码（训推一体主程序）
├── tools/                # 独立工具脚本（数据下载/转换/归档等，一次性或低频使用）
├── config/               # 配置文件（SOP YAML、训练超参等）
├── datasets/
│   ├── raw/              # 原始公开数据集（不入 git）
│   └── converted/        # 转换为 YOLO 格式后的数据（不入 git）
├── runs/                 # 每次训练/推理运行自动生成的产物（不入 git，见 01 §6）
│   └── YYYYMMDD-HHMMSS-<task>/
├── archive/              # 过时产物归档区
│   └── ARCHIVE_LOG.md    # 归档清单（唯一入 git 的归档文件）
├── exports/              # 对外导出副本（不入 git）
├── .venv/                # 项目内 Python 虚拟环境（隔离依赖，不入 git）
├── .gitignore
└── README.md
```

| 规则 | 说明 |
|---|---|
| 脚本归属 | 主程序进 `src/`；独立/一次性工具进 `tools/`；**其他位置不得出现 .py 文件** |
| 运行产物 | 一切训练/推理/转换过程产物只写 `runs/`，自动生成人可读摘要（见 01 §6），**不得写到根目录或临时位置** |
| 归档 | `runs/`、`datasets/converted/` 中过时条目由归档脚本移入 `archive/<类别>/`，随后 `archive:` 提交 git；归档仅记录清单，不提交大文件本体 |
| 环境 | 特殊依赖一律安装在项目内 `.venv/`，不污染全局；依赖清单固定在 `requirements.txt` |
